* **Creation**: Leerstands-Gate für `test`-Targets (`scripts/empty-test-targets.mjs`, CI-Schritt „Leerstand der test-Targets pruefen"). Seit #159 hat jedes Projekt mit eigenem Code ein Target, 45 der 86 davon ohne eine einzige Spec — und in der CI-Ausgabe ist ein leeres Target von einem vollen nicht zu unterscheiden. Beide melden grün. Das Gate macht den Leerstand messbar und bricht ab, sobald ein weiteres leeres Target dazukommt.
* **Update**: [Test-Target-Guide](../guides/lib-vitest-test-target.md) §5 beschreibt jetzt das Gate statt einer Zählung auf Zuruf, inklusive Konflikt-Rezept für die Baseline und der Antwort auf „neues Projekt angelegt, Gate rot".
* **Befund**: Die Baseline ist die **Liste** der leeren Projekte, kein Zähler. Ein Zähler wäre blind gegen den häufigsten Fall — Projekt A bekommt seine erste Spec (−1), Projekt B wird neu und leer angelegt (+1), netto 45, niemand sieht es. Dieselbe Begründung, aus der `mongo-raw-gate.mjs` in panary-cloud einen Zähler verworfen hat.
* **Befund**: Der Gate-Spec hatte zunächst eine wirkungslose Prüfung. Der Test gegen Namensvettern konstruierte einen Nachbarpfad, der nie einen echten Pfad im Projekt matchte — die Mutation „Pfadtrenner im Präfix-Vergleich weglassen" lief grün durch. Erst ein Fall mit einer Datei, deren Name mit dem eines verschachtelten Projekts beginnt (`domain-extra.spec.ts` neben dem Projekt `domain`), fängt sie. Ein Test, der nach einer Mutation grün bleibt, misst nichts — das gilt auch für Tests von Gates.
* **Befund**: Ein Zusatz-Check „Spec vorhanden, wird aber nicht geglobt" wurde geprüft und verworfen. Die einzigen Projekte mit Specs ohne per-Datei-`test-ci`-Targets sind `admin-client`, `setup-client` und `pos-client`; die fahren `@angular/build:unit-test`, der solche Targets grundsätzlich nicht anlegt. Der Check hätte drei Fehlalarme und null echte Funde.
