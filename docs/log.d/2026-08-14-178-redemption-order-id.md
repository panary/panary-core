* **Update**: Eine Rabattcode-Einloesung kennt jetzt ihre Bestellung. Bisher stand dort `orderId: null` — der POS loeste **vor** dem Anlegen der Order ein und kannte deren ID nicht (im Online-Pfad vergibt sie der Server, und `createOrder` liefert nur die `dailySequenceNumber` zurueck). Damit war keine Einloesung einer Bestellung zuzuordnen. Der POS vergibt die `_id` jetzt selbst (uuidv7) und reicht sie an beide Aufrufe; der Edge-Resolver uebernimmt eine mitgegebene `_id` ohnehin — derselbe Weg, den der Offline-Pfad seit jeher nutzt. Die Reihenfolge bleibt erzwungen: Erst einloesen, dann bestellen, sonst bekaeme der Gast bei aufgebrauchtem Code den Rabatt ungezaehlt. Schlaegt die Einloesung fehl, faellt die vorab vergebene ID weg. Gekapselt als `redeemCodeForOrder` in `promo-code.ts` — die Invariante „Order-ID und Einloesung gehoeren zusammen" ist dort getestet, inklusive der Gegenprobe, dass die uebergebene ID **dieselbe** ist wie die zurueckgegebene. Details: [ADR 0032](../adr/0032-promo-codes-am-pos-strikt-online.md), [Rabatte](../domains/rabatte.md).
* **Update**: `CreateOrderInput` nimmt ein optionales `_id` entgegen. Ohne das Feld bleibt die Vergabe wie bisher beim Server — gesetzt wird es heute nur im Rabattcode-Pfad. Der Offline-Pfad respektiert eine mitgegebene ID jetzt ebenfalls, statt sie zu ueberschreiben.
