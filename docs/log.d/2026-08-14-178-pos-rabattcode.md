* **Creation**: [ADR 0032](../adr/0032-promo-codes-am-pos-strikt-online.md) haelt die Weiche fest, an der das Feature haengt: Rabattcodes am POS sind **strikt online**. Die Alternative „optimistisch annehmen, spaeter abgleichen" liess sich beim Durchrechnen gar nicht bauen — der Edge kennt weder Code noch Rabattwert, „annehmen" hiesse den Kassierer den Wert eintippen zu lassen. Sie waere nur mit Code-Sync moeglich und damit eine Alternative zur Cloud-only-Entscheidung, nicht zur Offline-Frage.
* **Creation**: Edge-Service `discount-code-redeem` reicht Pruefung (`find`) und Einloesung (`create`) an die Cloud durch, statt Codes zu spiegeln. Erreichbarkeit wird am Aufruf gemessen (5 s Timeout), nicht am Sync-Zeitstempel — der sagt etwas ueber Datenaktualitaet, nichts ueber Antwortbereitschaft. Ein `401`/`429`/`5xx` zaehlt als unentschieden (`cloud_unreachable`), nie als „Code ungueltig": die fachliche Ablehnung kommt als `200` mit `ok: false`. Neue `AppResource.DISCOUNT_CODE_REDEEM` mit READ+CREATE fuer genau die sechs Rollen, die auch `discounts` lesen duerfen. Cloud-Gegenstueck: panary/panary-cloud#271.
* **Creation**: Kassendialog `PromoCodeDialogComponent` (Touch-Tastatur, Live-Rueckmeldung). Gepruefter Code wird gehalten, **eingeloest erst beim Bestellabschluss** — sonst verbrauchte ein Abbruch nach der Eingabe den Code, bei `usageLimit: 1` unwiederbringlich. Beim Abschluss prueft die Cloud erneut; scheitert es (andere Kasse war schneller), laeuft die Bestellung ohne Code weiter statt zu scheitern. Fachliche Ablehnung ist rot, technische amber — der Unterschied muss ohne Lesen erkennbar sein.
* **Update**: [Rabatte](../domains/rabatte.md) um den Abschnitt „POS-Anwendung (Rabattcode)" erweitert; der Offen-Punkt „POS-Code-Eingabe" ist erledigt, die Storefront-Haelfte bleibt offen.
